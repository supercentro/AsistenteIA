# Results of A2 + A2b (security properties, concurrency, privileges)

Date: 2026-11-23. Fictitious data only; no Gemini call; every database check ran on a throwaway `pgvector/pgvector:0.8.7-pg15` container on `127.0.0.1:55434` (its own cluster, removed afterwards). The development database and its server were only **read** (counts, task "state of each environment"); no migration, grant or write ran against any persistent environment. Both switches stay false by default.

| Any other environment | unknown | the rule is data-driven, so it needs no knowledge of it |

Rule of migration `0008`: the marker is set to the time of the migration for each subject that already holds conversations, and stays null for the others. In the development database it would mark the 4 subjects with messages (not applied).

## The property of V1 was corrected first

The first formulation (worlds that differ only in the removed student's messages) holds **without any mitigation** unless the student is re-enrolled (0 of 35 worlds differ on the reference model). The accepted property is independence from the whole cut-off past: worlds that differ only in messages created before the marker in force, by any student, give identical responses after the removal.

| System | Worlds that differ (25 seeds, the service, in memory) |
|---|---|
| Without the marker (control) | 25 of 25 |
| A2 + A2b | **0 of 25** |

The temporal property of A2b (worlds that differ only in the open week, including a student enrolled in it): 25 of 25 pass with A2b; with the open week let through the property fails (mutant M2).

## Limits of the evidence

- The reference model of the earlier round applied the rule by hand; these results are on the **implemented** service, but the random worlds use an in-memory repository (the filters of the SQL repository are covered by the integration tests with fixed data).
- Concurrency is deterministic by holding locks in a separate session (the project's pattern), not by stress.
- The read isolation is set by the dependency and tested on it; the race is shown on the service with the same options.
- Behaviour under a clock that goes backwards is not tested (`GREATEST` keeps the marker monotonic; the ordering argument assumes the database clock).
- The grant reaching an **existing** persistent environment is the documented `db-migrate` then `db-verify` flow; it was exercised on the throwaway cluster only, not applied anywhere persistent.
- F8, V3, F6 and F7 are untouched and stay open.
