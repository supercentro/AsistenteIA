# Design

## Context

Today every database client uses the bootstrap superuser of the official image: the API (`backend/.env`), the worker (`backend/.env.worker`), Alembic (`alembic/env.py` reads the API settings), the CLI, the integration tests (`TEST_DATABASE_URL`) and the CI service container. The development cluster has one role, no ACL on any table or type, no row-level security, no triggers, no own functions, no sequences (all keys are `gen_random_uuid()`), seven tables and two enums, all owned by that superuser. Two facts shape the design: pgvector is not a *trusted* extension, so only a superuser can run `CREATE EXTENSION vector` (migration `0001` does, and its downgrade drops the extension), and the running API container receives the superuser password and `TEST_DATABASE_URL` through `backend/.env`. See `proposal.md` for the motivation and `docs/technical-debt.md` (`TD-030`, `TD-038`) for the accepted state.

Evidence: the analysis, two independent adversarial reviews (24 and 13 findings) and two spikes on a disposable PostgreSQL 15.19 with pgvector 0.8.7 are in `reports/` (`2026-11-12-spike-summary.md`, `2026-11-12-independent-reviews.md`, `spike/`, `h13/`). This design records the decisions that survived them. Names such as `db-bootstrap` are working names.

## Goals / Non-Goals

**Goals:**
- Three working database identities with only the privileges the code needs, enforced by PostgreSQL and verified by tests that run the real API, CLI and worker.
- Grants that cannot silently disappear or be wrong: one declarative matrix, derived mechanically from the code, applied atomically with the migrations, checked by a read-only verifier.
- A start-up and rollout path that works from nothing with `docker compose up`, is idempotent, keeps existing data, and can be rolled back without data loss.
- Per-service secrets: no application container holds the administrator or migrator credentials.

**Non-Goals:**
- Row-level security, `SECURITY DEFINER` functions, a custom `pg_hba.conf`, moving pgvector out of `public` (owner decisions D4 and D7, 2026-11-12).
- Container hardening and the PDF sandbox (change 13), rotation of existing secrets (`TD-038`), production deployment, new product features.
- Preventing what direct table access makes possible for a compromised worker (chunk poisoning, reading pending payloads): recorded as technical debt.

## Decisions

Status of the decisions: **confirmed** by the owner on 2026-11-12: D1 to D8, the consent commit (designed here, implemented later) and the instruction to design the teacher separation; **proposed** for approval with these artifacts: DD-1 to DD-8 and DD-10 to DD-13 (they follow from D1 to D8 and from the evidence); **approved by the owner on 2026-11-12 after the group 2 request**: DD-9 option A as the target design (five identities); its implementation (group 8, migration `0006`) was authorised and delivered, and it is applied to the development database since 2026-11-14.

Owner decisions of 2026-11-12: D1 independent change; D2 specific environment files per concern; D3 permissions derived mechanically, `SELECT` on `document_chunks` kept for the API; D4 RLS, `SECURITY DEFINER` and `pg_hba.conf` out; D5 privilege tests are a mandatory CI gate; D6 spike on a disposable server; D7 pgvector stays in `public` and the privileged bootstrap manages the extension; D8 `TEST_DATABASE_URL` isolated in a test-only environment; plus the instruction to design (not implement) the teacher-provisioning separation and the consent commit.

**DD-1 Five identities.** Administrator (existing superuser, cluster administration only), `asistente_migrator`, `asistente_app`, `asistente_worker` and `asistente_cli` (working names; the CLI role is the owner's DD-9 decision and was implemented in group 8; until then the CLI used the application role). Alternatives: keep the superuser (rejected: it is the problem); two roles only, migrator merged with app (rejected: a SQL injection would own the schema); per-statement `SECURITY DEFINER` functions (out of scope, D4). The administrator keeps its current name, so the image, the health check and the guide commands do not change.

**DD-2 Roles live outside Alembic.** Roles are cluster objects with secrets and need `CREATEROLE`; the migrator has neither. The bootstrap creates them. Alternatives: roles in migrations (rejected: passwords in code history, migrations would need superuser).

**DD-3 One declarative matrix, derived mechanically, enforced three ways.** `app/db_privileges.py` holds the matrix; an inventory script lists every ORM attribute mutation, `insert/update/delete`, `RETURNING`, row-lock and raw `text()` statement of the API, CLI and worker, and a test fails if the code needs a privilege the matrix lacks or the matrix grants one no statement uses; a completeness test fails for a table without a decision; `db-verify` compares the live catalog. Alternatives: grants inside each migration (rejected: forgotten grants and environment-dependent migrations); default privileges only (rejected: they cannot express per-role, per-column limits). The matrix is the one **derived mechanically in group 2** (`reports/group-2/privilege-inventory.txt`, built by `backend/tests/privilege_inventory.py` from the call graph of the API, worker and CLI and the SQL of the repositories; `app/db_privileges.py` holds it and `tests/unit/test_db_privileges_*.py` prove it equals the inventory). Columns are listed whenever a grant is narrower than the table; a set equal to every column may be rendered as a table-level grant because a new column fails a test first.

Notes (what group 2 found, against the matrix of the spike):

1. **Registration still inserts `role`.** The code passes `role = student`, so the matrix keeps `role` out of the application `INSERT` (option A) and the test suite records the gap explicitly (`KNOWN_GAPS`): it must be closed by task 8.4 and the suite fails if the gap disappears without the code change or the grant appears early.
2. **Narrower than the spike matrix, but wider than the first derivation (group 5).** `INSERT` is column-level and the application role cannot read `ingestion_jobs.locked_by` (the fencing token), `locked_until` or `document_id`. The group 2 inventory assumed that the ORM lists only the columns passed to the constructor; **running the repositories under the roles refuted it**: SQLAlchemy sends every column without a server default, as `NULL` when unset. The matrix therefore also grants `INSERT` on `documents.error_message, error_code`, `users.consent_version, consent_accepted_at` (application and CLI) and `ingestion_jobs.locked_by, locked_until`. Consequences, all accepted and listed for `technical-debt.md`: a compromised API can create a job with a chosen token and a far-future lease (the job is never claimed), can queue an arbitrary payload for any document it knows, can insert documents with arbitrary `error_message`/`status`, and can set consent evidence on a new account (it could already update it). Making the ORM omit those columns (a server default of `NULL` without `RETURNING` of the fencing columns) is a possible later change. The API can also read queued upload bytes through `payload`. **Superseded on 2026-11-13 by DD-14:** the six extra `INSERT` columns were removed through `FetchedValue()` (and the four `SELECT` columns of `ingestion_jobs` that only the `RETURNING` needed); the consequences listed here no longer apply to the application and CLI roles.
3. **`document_chunks` for the application role is anticipated**, not derived: no endpoint reaches the retrieval query yet (`ChunkRepository.find_similar`). The suite grants it only through the named extra root and fails as soon as an entry point reaches the query, so the special case cannot outlive the chat change.
4. **Referential actions and foreign-key checks run as the table owner** (H1, kept `H1x` records), so no `DELETE` is needed on children and no privilege on referenced tables. The worker needs `SELECT (id)` on `document_chunks` because a single-row bulk insert is `INSERT ... RETURNING id` (derived by the inventory rule for Core inserts; the live failure was observed in the first spike run and is re-proved by the mutation of task 5.4). `UPDATE (consent_*)` on `users` is needed by the consent endpoint (A-01) and `SELECT (id)` follows from the flush of the attribute assignment.
5. **Dead code found:** `DocumentRepository.get_for_teacher` has no consumer in the application (only an integration test); it is declared in the suite and needs no grant of its own.
6. **Decision 2.5 (row lock on `subjects`): keep `SELECT ... FOR UPDATE` and the lock-carrier `UPDATE (description)`.** Evidence: any row lock, `SHARE` ones included, needs `UPDATE` on one column (`H2`, kept: HTTP 503 without it, 202 with it); the archived design A5 of `document-ingestion` relies on the row lock to serialise uploads of a subject and to yield the `404` for a subject deleted meanwhile, and `tests/integration/test_document_repository.py` pins that behaviour (a held subject lock blocks the upload of the same subject only, and the global advisory lock is taken after it). An advisory lock would not conflict with the foreign-key lock of a concurrent subject delete, so the race would surface as a foreign-key violation and need new handling and concurrency tests. The cost of keeping it is that the application role can change `subjects.description`; there is no endpoint for that. It is an analysis, not a measurement: it was not run against a database in this stage. Accepted residual risk (to technical debt in group 18); the advisory-lock alternative stays documented for a later change.

**DD-4 Table-level revoke, then grant, in one transaction (`db-grants`).** A column-level `REVOKE` does not remove a table-level grant, a table-level `REVOKE` removes both (H12), and a non-atomic revoke+grant produced permission errors for a concurrent reader (2 of 98 reads; 0 of 99 when atomic, B-03).

**DD-5 One entry point for migrations and grants (`db-migrate`).** Alembic runs, then the grants; grants vanish with a recreated table (A-07), so `alembic/env.py` refuses a direct run unless called through the command (or applies the grants in the same run). `MigrationSettings` replaces the API settings in `alembic/env.py`: the migration service no longer needs `JWT_SECRET`. `downgrade base` drops the extension and stays an administrator operation (A-13); the merged migration `0001` is not edited.

**DD-6 Hardened, idempotent bootstrap.** Administrator session with `options=-c search_path=pg_catalog` and schema-qualified names (`"public"."users"`, found necessary by the first live run: unqualified names fail under that path) (a function `lower(varchar)` or an operator `=(varchar, varchar)` planted in `public` wins over `pg_catalog` when `public` is in the path, B-01), role and database work from the `postgres` database, SCRAM verifiers computed by the client (H9), `ALTER ROLE ... RESET ALL` before the intended settings (a role can change its own password and settings, B-05), `PUBLIC` closed on the application database, on schema `public` and on every other database including the templates (A-09, A-08: `PUBLIC` keeps `USAGE` on `public` by default and the migrator cannot grant schema privileges), `CREATE EXTENSION IF NOT EXISTS vector`, and the global `ALTER DEFAULT PRIVILEGES FOR ROLE migrator REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` (the `IN SCHEMA` form has no effect, A-05). Runtime roles keep `search_path = pg_catalog, public` because they need the vector type and operators, and the **migrator keeps `public`** (an unqualified `CREATE TABLE` lands in the first schema of the path, so `pg_catalog` first made Alembic try to create in the catalog: found by the first live run); `ALTER ROLE ... IN DATABASE ... RESET ALL` also clears per-database settings and the bootstrap connection disables statement logging because its statements carry verifiers; that exposure to objects planted by the (trusted) migrator is mitigated by review and by `db-verify` listing foreign functions, operators and triggers with exact signatures.

**DD-7 Adoption is a separate, explicit, one-time command (`db-adopt`).** `ALTER TABLE ... OWNER TO` and `ALTER TYPE ... OWNER TO` with a `lock_timeout`, API and worker stopped, catalog and rows verified before and after (H10). `REASSIGN OWNED BY <administrator>` is rejected by PostgreSQL and is not used. The idempotent bootstrap only reports ownership drift (B-04). Alternatives: adoption inside the bootstrap (rejected: `ALTER OWNER` locks live tables on every `up` and hides drift).

**DD-8 Compose flow and environment files (D2, D8, A-03, A-04, B-02).** `db` (healthy) -> `bootstrap` (completed) -> `migrate` (completed) -> `backend` and `worker`, all in the **default profile** (a one-shot in an inactive profile that others depend on makes the whole project invalid, H13); both one-shots are idempotent because a plain `up` starts the finished containers again; credentials change with `up -d` (Compose recreates a service whose environment changed) and never with `restart`. Files: `backend/.env` (API: application-role URL, JWT, CORS; no `POSTGRES_*`, no `TEST_DATABASE_URL`), `backend/.env.worker`, `backend/.env.db` (administrator, database container only), new `backend/.env.migrate` (migrator URL), new `backend/.env.roles` (administrator password and the three role passwords, bootstrap only), new host-only `backend/.env.test` (never passed to a container). Variable names fixed in group 3: `MIGRATION_DATABASE_URL` (`MigrationSettings`, deliberately not `DATABASE_URL`, so a migration run with the API environment fails instead of using another credential); `ADMIN_DATABASE_URL`, `DB_MIGRATOR_PASSWORD`, `DB_APP_PASSWORD`, `DB_WORKER_PASSWORD`, `DB_CLI_PASSWORD` (`RolesSettings`); `TEST_DATABASE_URL`, `TEST_ADMIN_DATABASE_URL`. Consequence: a manual `alembic` in a container that only has the API environment now fails by design; until the migrator exists the guide gives an explicit one-liner that passes the URL knowingly. The one-shots use the image, not the source bind mount; `up --build` is required when `app/` or `alembic/` change. The API's read-write source mount, visible to the read-only worker, stays a recorded residual risk of change 13 (A-06).

**DD-9 Teacher provisioning is separated from public registration at database level (option A approved by the owner on 2026-11-12; implemented in group 8 and applied to the development database on 2026-11-14).** At the time of the decision the runtime role could `INSERT` a `users` row with `role = 'teacher'` (proved), so "teachers only by CLI" holds only in code. Options:

| Option | What it is | Complexity | Tests | Verdict |
|---|---|---|---|---|

Decision (owner, 2026-11-12): option A is the target design: a separate CLI role, a registration path that cannot create teachers because the application role has no `INSERT` on `users.role`, a server default `'student'` on `users.role` through the reversible migration `0006`, and positive and negative tests. Group 8 of `tasks.md` implements it and needs its own authorisation; nothing of it exists yet (no role, no migration, no code). The `role-based-access` delta describes the target behaviour.

**DD-10 Consent endpoint: explicit commit.** `POST /users/me/consent` mutates the ORM object and relies on the commit of the `get_db` dependency, which runs after the response left; a refused write therefore returned `200` with nothing stored (N-1, proved). Document upload and delete already commit explicitly. The fix is an explicit `commit()` before returning (consistent with the precedent in `documents.py`), with a persisted-state test, applied as a separate functional commit in group 7; the rule "an endpoint that promises persistence commits explicitly" goes to `docs/backend-standards.md`. Subjects, enrollments and registration already flush inside the handler, so a refusal gives a 500 there.

**DD-11 Tests (D5).** Layers: matrix and inventory unit tests; catalog tests for roles, ownership, default ACLs and `db-verify`; the denied-operation suite (69 refusals proved plus the attribute check); atomic grants with a concurrent reader; planting tests for functions and operators in `public`; self-tampering tests (`ALTER ROLE self`); the role-bound integration suite that runs every API route, every CLI subcommand and the worker paths under the roles and **asserts persisted state**; rollback and adoption on a database with data. Isolation: a `*_test` database of its own, role names with a reserved prefix that cannot match real names and a sweep of leftovers, an administrator URL in the host-only file, failure (not skip) when it is missing; the existing guard keeps comparing with the application `DATABASE_URL` (B-08). `drop_everything` leaves no schema ACL and no extension, so the role-bound fixtures rebuild connection rights, schema ACL and extension before running Alembic as the migrator (A-14). The CI service container already has a superuser, so the privilege job can create the roles; the Compose behaviour is validated by the scratch-project run (H13) and repeated manually with the real commands.

**DD-12 Rollout and rollback.** Verified backup and restore rehearsal as for migration `0005` (`docs/development_guide.md`); full rehearsal of bootstrap, adoption, grants, `db-verify`, the 45+17 functional checks and the rollback on a restored copy; the real run is a separate authorisation. Rollback per database: `REASSIGN OWNED BY migrator TO <administrator>`, verify owners, `DROP OWNED` for the three roles (it then only revokes, including `CONNECT`), re-grant what must remain, `DROP ROLE` only when every database is clean; never `DROP OWNED` before reassigning (it dropped all tables in the spike, A-02). Pointing both `DATABASE_URL` values back to the administrator is an instant, data-neutral **emergency** fallback because the administrator keeps working throughout; it reintroduces the superuser into the API and worker environment, so it must be reverted afterwards and the exposed credential rotated (`TD-038`).

**DD-13 Residual risks become technical debt** (new entries at implementation time, none solved by roles): R1 a role can change its own password and settings (detected by login probe, healed by the bootstrap); R2 a compromised worker can insert chunks for any existing document, read pending payloads and set document status; R3 the runtime role can insert teacher accounts until DD-9 is implemented; R4 roles with table-level `UPDATE`/`DELETE` can `LOCK TABLE` (availability); R5 the API-writable source mount seen by the worker (change 13); R6 `trust` authentication inside the database container (D4); R7 large objects, `pg_sleep`, user-settable timeouts; R8 a failed `ALTER ROLE ... PASSWORD` logs the verifier; R9 the migrator, as table owner, can plant functions, operators and triggers (review plus `db-verify`; the administrator never touches application objects and uses `search_path = pg_catalog`); R10 a single backup copy.

**DD-14 Narrow `INSERT` through `FetchedValue()` (owner authorisation of 2026-11-13; supersedes the provisional wide lists of note 2).** The ORM sends every column without any default as `NULL`, which forced six extra `INSERT` grants (proved in group 5, analysed in `reports/group-6/orm-insert-columns-analysis.md`). The six columns get `server_default=FetchedValue()` (a marker, no DDL, no migration; `alembic check` does not compare server defaults) and `IngestionJob` gets `eager_defaults=False`, so its `RETURNING` asks only for the key and the application role needs no `SELECT` on the fencing token. For `documents` and `users` the application and CLI roles already read every column, so the default `RETURNING` needs nothing new. Order: `ingestion_jobs`, then `documents`, then `users`, one commit each, matrix narrowed only after the SQL inspection test proves the columns left the `INSERT`. If `FetchedValue()` changes a semantic or needs an extra `SELECT`, work stops and an alternative (Core insert in the repository) is presented. **Rule that follows from `eager_defaults=False` on `IngestionJob`:** its attributes other than the key are expired after a flush, so any future API code that reads `job.attempts`, `available_at`, `created_at` or the lease from that object would issue a `SELECT` that the application role is denied (a permission error, by design); such a read needs a new matrix decision first.

**DD-15 Explicit commit for every endpoint that promises persistence (TD-039).** `get_db` commits after the handler, which in the current stack happens after the success response was sent, so a refused commit followed a 2xx (proved for the consent endpoint, DD-10). Registration, subjects and enrollments get the same pattern as the consent endpoint and `documents.py`: the handler calls `commit()` before building the response, rolls back and re-raises on error; the `get_db` commit that follows has nothing left to write. The service and repository layers keep flushing (they do not commit), so service-level units of work are unchanged.

**DD-16 Corrections of the independent review (task 15.2, owner authorisation of 2026-11-13).** (1) PG-01: the API and the worker refuse to start as a superuser. The check asks the server (`current_setting('is_superuser')` and `pg_roles.rolsuper` for `current_user` and `session_user`), runs in the production entry points (`app_factory`, `app.worker.main`) and not in `create_app` or `run_worker` called in process by the unit tests, fails closed when the database cannot be reached, and has one escape, `ALLOW_SUPERUSER_DATABASE_ROLE`, that the settings reject unless `APP_ENV=test` (the real-server and real-process tests run on throwaway clusters as the owner). Consequence for this machine: the running development stack still uses the owner (TD-040), so a restart of its API or worker is refused until group 17 gives it the restricted URLs; no real file was changed. (2) PG-02: `db-migrate`, `db-downgrade` and `db-verify` open a first connection and require `current_user` = migrator before Alembic or any statement. (3) F-1, B-1, F-2: `DELETE` of a document uses the shared `commit_or_rollback`; the contract documents `500` and `503` for the seven operations; the `InternalError` wording no longer claims that nothing was stored (a connection lost at commit is an uncertain outcome and is a 503). The error mapping of the upload (every database error is a 503, F-4) is left as documented: changing it changes an existing contract and is not part of this task. (4) PG-07, PG-08: system databases are refused as targets; the rollback acts on the named database, reports the databases where the migrator still owns objects, and removing the roles stays refused until none is left. The row counts inside the adoption lock, the per-database rollback transaction and the cluster-wide closing of PUBLIC are recorded as accepted limits, not changed, because changing them changes the adoption procedure.

## Risks / Trade-offs

- A matrix derived from today's code can lag behind tomorrow's: the inventory test and `db-verify` make a missing or extra privilege fail the build instead of production.
- Failure modes look like capacity or authentication errors (connection limits, a changed password, a silent `200`): the persisted-state tests and `db-verify` are the controls, not the application logs.
- One-shot services run on every `up`: they must stay fast and idempotent, and a failure blocks the stack by design.
- Option A of DD-9 (approved) needs a migration and a small code change in the registration path; until group 8 was implemented the runtime role could still insert teachers (recorded; closed in group 8).
- `FetchedValue()` is a marker, not a database default: a new nullable column added without a decision would again be sent as `NULL`; the matrix comparison (a column without a decision) fails first. Expired attributes after a flush trigger a `SELECT` on access: for the fencing token that `SELECT` is refused, which is intended, and no code reads it.
- The stand-ins used for H13 prove the Compose behaviour, not the commands; task 6.4 repeats the run with the real ones.
