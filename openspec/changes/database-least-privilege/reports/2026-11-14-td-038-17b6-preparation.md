## 2. Corrections made to the tools (lessons of SEC-17B-01 applied to the administrator tools)

`rotate_admin_password.py`: no traceback or echo on any unexpected error (type only); the Windows ACL script is mandatory for `apply`, `rollback`, `discard` and `cleanup` (dry runs exempt); every target is restored once the replacement phase starts (an interruption between `os.replace` and its bookkeeping no longer leaves a rotated file behind); `apply` lists the recovery copies that keep the old value; new `discard` command. `rotate_db_role.py`: generic handler (type only, exit 4 for local errors, 3 reserved for "the server may have changed"), new `--as-url` probe that takes the password from the userinfo of a stored URL variable and refuses a URL of another user. `check_containers_for_value.py` (existing) is used by step 0b and step 9 and now also matches Go's JSON escaping of `&`, `<`, `>`.

## 3. Facts established, not assumed

| Question | Answer and evidence |
|---|---|
| Does changing `POSTGRES_PASSWORD` change the password of an existing role? | **No.** The image reads it only to initialise an empty data directory. Disposable test: a container recreated with the new value only still accepts the OLD password and rejects the new one. The password lives in the data directory and changes only with `ALTER ROLE` |
| Is recreating PostgreSQL necessary? | **Not for authentication.** The rotation is complete and valid after `alter` + `apply`. Recreation (step 9) is hygiene and consistency: it removes the dead old value from `docker inspect` of the container and stops the next plain `docker compose up` from recreating `db` at an arbitrary moment, because Compose detects the changed `env_file`. It is the owner's choice: recreate (recommended) or defer |
| Can the data be lost? | Not with `docker compose -p asistenteia up -d --no-deps --force-recreate -t 60 db`: the named volume is kept and the init scripts run only on an empty data directory. Disposable test: marker row, ownership, grants and role verifiers identical after the recreation. Danger: another project name or directory would create a NEW empty volume; the procedure records the mounted volume before and checks it after. Never `down -v` |
| Does the rotation reset the migrator password or change grants and ownership? | **No.** The tool changes only `POSTGRES_PASSWORD` of `.env.db` and URL variables whose user is the administrator (it refuses if the old value would stay anywhere else, including `DB_*_PASSWORD`); `ALTER ROLE` touches one role. Disposable tests: the synthetic migrator and application roles keep their verifiers, an object owned by the migrator keeps owner, grants and data. Even a stray `bootstrap` would re-set the migrator to the current `.env.roles` value, which is the new one |
| Is it possible to run `bootstrap` by accident? | `docker compose up`, `run` or `start` of the project would start it as a dependency of `migrate`. Procedure: forbidden from step 4 until the end of step 8. Effect if it happens between steps 4 and 6: fails closed (old URL), nothing changes, `backend` and `worker` are not started or recreated |
| What does the API and the worker feel if `db` is recreated? | 10 to 30 s without a database: `pool_pre_ping` reconnects the API; the worker's step loop logs the error type and retries (read in `app/worker.py`); in-flight requests and jobs in that window fail, so the procedure asks for an idle queue |
| How is the old password proven invalid? | Probe over the Docker network with the value taken from the `.env.db.old` copy: rejected; probes with the new value from the new file and from the three stored forms (`POSTGRES_PASSWORD`, `ADMIN_DATABASE_URL`, `TEST_DATABASE_URL`): accepted |
| Is there a lock-out? | No. `alter` runs `psql` inside the database container over its local socket, so it works without the old or the new password as long as the container runs |

## 6. Independent adversarial reviews (clean context, read only, no real env file opened)

**Review 1** (GO, two MAJOR, both fixed): recovery row 7 offered "A or B" in a state where B is refused and A makes it worse (now split by state); no stated escape from a lock-out (new row: `alter` runs `psql` inside the container over its local socket, so no password is needed while it runs). Minors fixed: recreate with `-p asistenteia` and a same-volume check, idle queue, `-t 60`, exit code 4 for local errors, `discard` precondition, Go JSON escaping in the scan, the mutant file kept out of the repository, unit tests for `--as-url`.

**Review 2** (NO-GO for one new MAJOR; the two earlier MAJOR confirmed fixed): **N1** - a hard kill while a `.old` copy was being written could leave an EMPTY or partial `.old`, and `rollback` restored every existing `.old` without checking, so a live env file could be replaced by an empty one. **Fixed** (administrator and role tools): each copy is written through a temporary name and `os.replace`d; a `.backup-complete` marker is written after all copies are verified and BEFORE any live file is touched; `rollback` refuses without the marker or when a listed copy is missing, empty, a link or of another size. Minors fixed: `alter --require-superuser` (a mistyped `--role` can never alter a restricted role; mandatory in the procedure), `cleanup` needs `--i-know-this-removes-the-only-file-rollback` (the `*.pre-17b` copies cannot be removed by accident), README `<admin>` defined, rows for "database OLD + files mixed" and for a revert source without `.old`, exit 130 on Ctrl-C of `alter`/probe. The real `pg_hba` was read read-only: one `local ... trust` and one `host ... scram-sha-256` rule, as the claim needs; the e2e also checks it on the disposable container.

**Review 3** (focused on the N1 fix; GO): minor fixes afterwards - an `.env.test` with nothing to rotate no longer makes a zero-byte backup that would block every rollback, Ctrl-C of `rollback`/`discard` exits 130, README names the hidden `.tmp` leftovers.

**Hardening round requested by the owner** (SHA-256 of the copies, rollback with a same-size swap, interruption while the marker is created, concurrent runs, no credentials in output): the marker now holds name, size and SHA-256 of every copy and is written to a temporary name, fsynced and renamed (an interrupted write leaves no marker, and then no live file was touched); `check_backup` refuses a copy of the same size but other content; `apply` takes an exclusive `.apply.lock` in the backup folder (of two concurrent runs exactly one proceeds; a folder left by a killed run is never reused); `discard` and `cleanup` overwrite and remove the hidden leftovers (`..env.<name>.old.tmp`, `.backup-complete.tmp`, `.apply.lock`, never a hard-linked file).

**Review 4** (GO, no blocker, no major) of that round, and **review 5** (GO, no blocker, no major) of the last tranche. Fixed from them: `restore` writes the bytes that were verified (the digest-checked copy for a rollback, the in-memory originals for a failed apply) instead of reading the `.old` a second time, and fsyncs its temporary file; `check_backup` also refuses a marker that lists fewer files than the copies present; the role tool also exits 130 on Ctrl-C; the README lists every variable to unset and every statement about rollback, lock and leftovers was checked against the code; the hostile-file tests now scan the backup folder and the temporary files for the new password. **Left as accepted minors:** a hard-linked leftover is skipped silently and `discard` still reports OK (it needs the owner to create the link); the lock covers the backup folder, not the env folder, so two applies with DIFFERENT backup folders could interleave (the procedure forbids it, `plan` refuses leftovers and the post-check fails closed); a Ctrl-C between taking the lock and the protected block leaves the lock in an otherwise empty folder (use a fresh folder).

## 7. Residual risks, window, requirements and decision

**Residual risks.** The administrator password stays valid until the owner authorises the rotation; it exists in six git-ignored files and three transcript files, and the three `*.pre-17b` copies keep the old, dead value after the rotation (their clean-up is NO-GO and the tool refuses it without an explicit flag); a recreation of `db` costs 10 to 30 s of unavailability and a failed one needs recovery C; `alter` is the point of no return; the probes prove the stored forms of the password, not every program that may hold it; the scan does not cover `docker logs` or image layers; `reject` probes cannot tell a wrong role name from a wrong password; the accepted minors above. **To confirm before the window on Windows:** the real-ACL path (the Read-only ACL of a temporary copy followed by the rename, which needs delete rights on the backup folder) is exercised by the e2e with the real `secure_file_acl.ps1`, which passed; the first command of the window repeats the ACL check of step 0a.

**Recommended next window.** At least 60 minutes with the stack running, a quiet moment with an idle worker queue, at least 8 GB of free RAM, the owner reachable and deciding any rollback that writes. Controlled recreation of ONLY the `db` container (`docker compose -p asistenteia up -d --no-deps --force-recreate -t 60 db`) keeping the same PostgreSQL volume (its name is recorded before and compared after), with a possible 10 to 30 s interruption of the API and worker, backend and worker validated afterwards, and any recovery subject to the owner's express authorisation. No window is set without the owner's confirmation.

**Requirements to run 17B.6.** A NEW explicit owner message naming the head commit, the window and the contact; the new-password file prepared by the owner outside the repository (no BOM, owner-only ACL, one line of 32 to 128 letters, digits, `-` or `_`) and stored in the password manager; an absent or empty `<BACKUP>` outside the repository; the decision between recreating `db` (recommended) and deferring; no `docker compose`, `bootstrap` or orchestrator process during steps 4 to 8; test variables unset.

**Decision: GO (technical) for the owner to authorise the administrator rotation in a future window.** The decision is the owner's; nothing here authorises anything.

**Not done:** no `ALTER ROLE`, no real `.env` change, no `docker compose` against the real stack, no recreation or restart of PostgreSQL, backend or worker, no `db-bootstrap`, no `JWT_SECRET` or other role rotation, no deletion of `migrator-new-password.txt`, no cleanup of `*.pre-17b`, no change of the privilege matrix, no push, PR or merge.
