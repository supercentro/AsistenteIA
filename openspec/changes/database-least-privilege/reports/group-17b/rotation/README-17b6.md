# Step 17B.6: rotation of the administrator password (TD-038). PREPARED AND TESTED ON DISPOSABLE RESOURCES; NOT RUN, NOT AUTHORISED

Revised on 2026-11-14 after the real rotation of `asistente_migrator` (SEC-17B-01), whose two independent reviews and the real run changed the tools and the rules. Impact matrix, differences from SEC-17B-01, review and window: `../../2026-11-14-td-038-17b6-preparation.md`.

Tools (this folder): `rotate_admin_password.py` (env files: plan, apply, verify, rollback, discard; cleanup is NO-GO), `rotate_db_role.py` (the SQL step and the network probes), `check_containers_for_value.py` (containers carrying a value). Tests: `test_rotate_admin_password.py` (file level, with mutations), `test_rotation_e2e.sh` and `test_rotation_e2e_mutations.sh` (disposable PostgreSQL, synthetic credentials). Decision on `.env.test`: `env-test-decision.md`.

## Rules that hold for every command below

- The new password lives in a file **outside the repository** and is never typed, printed, put in a command line, a generated script, a log or an evidence file. The tools print names and verdicts only and never a traceback (any unexpected error shows its type only). Output of any command that could echo a URL is piped through `sed -E 's#(postgres[a-z+]*://)[^ ]+#\1<redacted>#g'`.
- Run only after the owner accepted the previous step and authorised 17B.6 in a NEW message (no earlier authorisation is reusable).
- On Windows **`--acl-script` is mandatory** for `apply`, `rollback`, `discard` and `cleanup`; the tools refuse without it. `ROT_TEST_NO_ACL`, `ROT_TEST_FAIL_AT`, `ROT_TEST_HOOKS` and `ROT_DOCKER_CMD` must be unset in the shell.
- `alter` (step 4) always runs **before** `apply` (step 6). Ctrl-C during `alter` or a probe exits 130: for an `alter` the state is unknown, probe before anything else. Exit codes of `rotate_db_role.py`: 0 ok, 1 refused or expectation failed, 2 usage or missing file, 3 the server rejected the statement or the container did not answer (the change may have been committed: probe), 4 a local error (unreadable file, no docker client, unexpected exception: nothing was sent). The new-password file has no BOM (`rotate_db_role.py` rejects a BOM).
- Between steps 4 and 6 and until step 8: no `docker compose up`, `run` or `start`, no `db-bootstrap`, no orchestrator stage, no host reboot. (Unlike SEC-17B-01, a stray `bootstrap` cannot revert the administrator password, because `bootstrap` never sets it; but it authenticates with `ADMIN_DATABASE_URL`, so while `.env.roles` still holds the old value it FAILS CLOSED and a plain `docker compose up` would leave `backend` and `worker` created and not started.)
- Backend and worker are never edited; only the database container may be recreated (step 9, the owner's choice). Never `docker compose down -v`.
- `<admin>` is the `POSTGRES_USER` of `.env.db`: the only superuser role (`asistente`). Every `alter` of this procedure carries `--require-superuser`, which makes the tool refuse and change nothing for any role that is not a superuser, so a mistyped `--role` can never alter a restricted role. `<BACKEND>` is the real `backend` folder, `<NEWFILE>` the new-password file, `<BACKUP>` an absent or empty folder outside the repository and outside `<BACKEND>`, `<ACL>` is `group-17c/tools/secure_file_acl.ps1`, `<TOOLS>` this folder. Use Windows paths for `python` and `powershell`, and `export MSYS_NO_PATHCONV=1`.

## Owner's part (before the window; the operator never creates or reads this)

1. Create `<NEWFILE>` outside the repository: `python -c "import secrets; print(secrets.token_urlsafe(36))"` written as ASCII/UTF-8 without BOM, one line, 32 to 128 letters, digits, `-` or `_` (a PowerShell `>` redirect writes UTF-16 and is refused). The value is not shown.
2. Restrict it: `powershell -NoProfile -ExecutionPolicy Bypass -File <ACL> -Path <NEWFILE> -Rights Modify` (one rule, owner only; the inherited ACL of the folder is not enough).
3. Copy the value into the password manager and check the entry. Nothing else keeps it; keep the file until the rotation is complete, then delete it.

## Recovery (step 4 is the point of no return)

| Row | Where it fails | State | Action (the owner decides any command that writes) |
|---|---|---|---|
| 0-3 | before `alter` | nothing changed | fix the cause |
| 4 | `alter` exit 3 or uncertain | the database may hold the old or the new value | read-only: probe NEW from `<NEWFILE>` and OLD from `.env.db`; whichever is accepted is the truth; `alter` can simply be repeated |
| 5 | `alter` done, a probe is unexpected | files still old | read-only probes first; do not run `apply` until new accepted and old rejected |
| 6 | `alter` done, `apply` failed | database NEW; the tool restored the files (OLD); `docker compose`/`bootstrap` would fail closed | **B, forward (preferred)**: fix the cause, `apply` again with a NEW empty `<BACKUP>` folder (keep the first until the end). **A, revert (last resort, reinstates the exposed password)**: `rotate_db_role.py alter --container asistenteia-db-1 --role <admin> --require-superuser --from-env-file <BACKUP>/.env.db.old --var POSTGRES_PASSWORD` (if `apply` failed before its backup phase finished there is no `.old`: use `<BACKEND>/.env.db`, which was never touched), then the probes of step 3 (old accepted, new rejected); retry from step 1 with a new `<BACKUP>`. If exit 3 or the process was killed: look at `<BACKUP>` first. **`.backup-complete` present** (it is written after every `.old` was written and verified, and BEFORE the first live file is touched): `rotate_admin_password.py rollback <BACKEND> --backup-dir <BACKUP> --acl-script <ACL>` (restores byte for byte, removes orphan temporaries, safe to repeat; it refuses by itself if a `.old` is missing, empty or of another size), compare each file with its `.old` copy by size and hash, then A or B. **No marker**: no live file was replaced yet, nothing to roll back (`rollback` refuses on purpose): delete the partial `<BACKUP>` content by exact name and start again from step 1 |
| 7 | probes after `apply` unexpected | files and database disagree. Read-only probes say which way | **database OLD, files NEW** (for example a `bootstrap`, or anything else, put the old password back): run `rotate_db_role.py alter ... --password-file <NEWFILE>` again (forward); `apply` would be refused because the files already hold the new value. **Database NEW, a file OLD or mixed**: `rotate_admin_password.py rollback` first, then row 6 (B preferred). Never A when the files are already NEW. **Database OLD, files mixed**: `rollback` (every file back to the old value), probe, then `alter` forward and `apply` |
| 8 | `db-verify`, snapshot, health or sessions unexpected | the rotation changes nothing but the administrator password, so this is not caused by it | stop and report; no rollback of the rotation unless a probe says so |
| 9 | the recreated `db` is not healthy | the volume is untouched and holds the new password | **C**: read the container log (names only, redacted), `docker compose up -d --no-deps db` again; the container only needs `.env.db` with the new value (`verify` checks it). Never `down -v`, never `prepare_env_files.py --rollback` in any of these states |
| any | **lock-out**: the new-password file was lost, or the files were restored to the old value while the database holds the new one | the old password is not needed to recover: `alter` runs `psql` INSIDE the database container over its local socket (`docker exec`, trusted by `pg_hba` `local`), so it works whatever the password is, as long as the `db` container runs | the owner creates a NEW new-password file (and stores it in the manager), then `alter` with it, then `apply` (a new empty `<BACKUP>`). If `db` itself is down: `docker compose up -d --no-deps db` first (recovery C) |
| any | the owner wants to undo 17B after the rotation | new administrator password everywhere | `prepare_env_files.py --rollback` rebuilds `.env` and `.env.worker` with the administrator password of the CURRENT `.env.db`, as long as the `*.pre-17b` copies exist (they keep the old, dead value; cleanup is NO-GO precisely because of this) |
| any | `bootstrap` or `docker compose up` ran between steps 4 and 6 | `bootstrap` failed closed (old `ADMIN_DATABASE_URL`); nothing changed except possibly an unwanted recreation of services | read-only probes, then continue at step 6 |

A killed process can also leave hidden `.<name>.old.tmp` files in `<BACKUP>`: they hold the old value too and are deleted by exact name by hand. After a failed or rolled-back `apply` the `*.old` copies hold the STILL-LIVE old value and `discard` refuses (the live files hold it too): delete them by exact name by hand once the rotation is finished or abandoned. Backups needed to recover: `<BACKUP>/*.old`, `<NEWFILE>`, the two PostgreSQL dumps, the `*.pre-17b` copies and the `pre-17b` image tags.

## What was proven (disposable PostgreSQL 15.19 + pgvector 0.8.7, synthetic credentials)

The password never appears in any argument of any process (a recording wrapper around the docker client logged every argument), nor in the tools' output; the server accepts the verifier computed here; the new password is accepted and the old one rejected over the network before and after recreating the container; **`POSTGRES_PASSWORD` alone does not change the password of an existing role** (a container recreated with the new value only still accepts the old password); the container environment is irrelevant until recreated; the rotation leaves the synthetic migrator and application roles (their verifiers), the ownership of an object, its grants and its data unchanged; the data volume survives the recreation; the container scan finds the database container before the recreation and not after; partial failure with both recoveries; interruption between `os.replace` and its bookkeeping; no traceback and no echo for a non-ASCII URL; refusal on Windows without `--acl-script`; `discard` removes only the `*.old` copies. Shell history: no secret is ever a command-line word.

## Limits (so nobody over-reads it)

`--expect reject` also passes for a role that does not exist (PostgreSQL answers "password authentication failed" for it too): the accept probe of the new password in step 7 covers a typo in `--role`. `verify` looks at the env files of the folder only (not subfolders) and requires the administrator URLs of `.env.test` to carry the new value. The probes prove the stored forms of the password, not every program that may hold it. The scan covers container configuration (raw, percent-encoded, JSON-escaped), not `docker logs` or image layers. The overwrite-before-delete of `discard` is best effort on an SSD or a journalling file system. The recovery copies `*.pre-17b` keep the old value (dead after step 4) until a later decision. The tools protect against accidents, not against an operator who edits them. The database server log is not inspected; `alter` never sends the cleartext, so a statement log would contain only a verifier.
