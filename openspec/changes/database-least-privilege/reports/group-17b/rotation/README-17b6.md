# Step 17B.6: rotation of the administrator password (TD-038). PREPARED AND TESTED ON DISPOSABLE RESOURCES; NOT RUN, NOT AUTHORISED

Tools (this folder): `rotate_admin_password.py` (env files: plan, apply, verify, rollback, cleanup), `rotate_db_role.py` (the SQL step and the network checks). Tests: `test_rotate_admin_password.py` (83 checks, 11 mutations), `test_rotation_e2e.sh` (38 checks on a disposable PostgreSQL with synthetic credentials), `test_rotation_e2e_mutations.sh` (5 mutations). Decision on `.env.test`: `env-test-decision.md`.

Rules that hold for every command below: the new password lives in a file **outside the repository** and is never typed, printed, put in a command line, a generated script, a log or an evidence file; the tools print names and verdicts only; run it only after the owner has accepted 17B.5 **and** authorised 17B.6 in a new message; the services keep running (nothing but the database container is recreated). `<BACKEND>` is the real `backend` folder, `<NEWFILE>` the new-password file, `<BACKUP>` an empty folder outside the repository and outside `<BACKEND>`, `<ACL>` is `group-17c/tools/secure_file_acl.ps1`, `<TOOLS>` this folder. Use Windows paths for `python` and `powershell`, and `export MSYS_NO_PATHCONV=1`.

## Owner's part (before the window; the operator never creates or reads this)

1. Create `<NEWFILE>` outside the repository with a value of letters, digits, `-` and `_` (48 characters from `python -c "import secrets; print(secrets.token_urlsafe(36))" > <NEWFILE>`; the value goes to the file only, it is not shown) and restrict it: `powershell -NoProfile -ExecutionPolicy Bypass -File <ACL> -Path <NEWFILE> -Rights Modify`.
2. Copy the value from that file into the password manager entry. Nothing else keeps it.

## Recovery (the order of the procedure makes step 4 the point of no return)

- **A, revert** (files could not be updated, or the checks of step 7 fail): `python -I <TOOLS>/rotate_db_role.py alter --container asistenteia-db-1 --role asistente --from-env-file <BACKUP>/.env.db.old --var POSTGRES_PASSWORD`, then the probes of step 3 (old accepted) and `rotate_db_role.py probe ... --password-file <NEWFILE> --expect reject`. The files already hold the old value (the tool restored them). Retry from step 1 when the cause is fixed, with a NEW empty `<BACKUP>` folder (keep the first until the end). Delete the backups only after the rotation is complete.
- **B, forward** (the files failed but the database already has the new value): fix the cause the tool named and run step 5 again with a NEW empty `<BACKUP>` folder (keep the first one until the end), then continue from step 6.
- **C, the database container does not come up healthy** after step 6: the data volume is untouched and holds the new password; the container only needs `.env.db` with the new value (check `verify`); recreate it again. Never run `prepare_env_files.py --rollback` in any of these states.
- **The process was killed in the middle of `apply`** (a closed window, a power cut: the tool cannot catch that): run `python -I <TOOLS>/rotate_admin_password.py rollback <BACKEND> --backup-dir <BACKUP> --acl-script <ACL>`: it restores the originals byte for byte and removes the orphan temporary files (`..env.db.rot-<pid>` and similar, which can hold the old or the new value). `apply`, `plan`, `verify` and `cleanup` refuse to run while such files exist. Then follow A or B according to whether the `ALTER ROLE` of step 4 had been done (the probe of step 3 with the current password tells).
- **Tool failure with exit 3** (`ROLLBACK INCOMPLETE`): stop; compare each file with `<BACKUP>/<name>.old` by hand (sizes and `sha256sum`, never by opening them in a shared view) and restore the differing one with `rotate_admin_password.py rollback <BACKEND> --backup-dir <BACKUP>`.

## What was proven (disposable PostgreSQL 15.19 + pgvector 0.8.7, synthetic credentials, `g17b-rotation-e2e-output.txt`)

The password never appears in any argument of any process (a recording wrapper around the docker client logged every argument: zero hits for the old or the new value; the standard input of the SQL step carries only the SCRAM verifier; the probes send the password on the standard input of a throw-away container, which the wrapper forwards without logging), nor in the tools' output; the server accepts the verifier computed here; the new password is accepted and the old one rejected over the network, before and after recreating the container; the container environment is irrelevant until it is recreated; partial failure with both recoveries; clean-up leaves no old value in any file of the fixture; an unknown container, a malformed password file and a role name that is not an identifier are refused. Shell history: no secret is ever a command-line word, so none can reach the history; the operator types paths only.

## Limits (so nobody over-reads it)

Before the window confirm that `ROT_TEST_HOOKS` and `ROT_DOCKER_CMD` are NOT set in the shell (they redirect the docker client for the tests and would see the standard input). `verify` looks at the files of the env folder only (not subfolders) and requires the administrator URLs of `.env.test` to carry the new value. A tool run needs a UTF-8 or ASCII new-password file (a PowerShell `>` redirect writes UTF-16: the tool refuses it). `apply` keeps the originals in `<BACKUP>` until `cleanup`: they hold the OLD (exposed) value; every target, including `.env.db`, and every backup and temporary file gets the owner-only descriptor when `--acl-script` is given (pass it). The overwrite-before-delete of `cleanup` is best effort on an SSD or a journalling file system. A probe sends the password on the standard input of a throw-away container and exports it only inside that container (not in any argument and not in the container configuration or `docker inspect`). The tools protect against accidents, not against an operator who edits them. The database server log is not inspected; `alter` never sends the cleartext, so a statement log would contain only a verifier.
