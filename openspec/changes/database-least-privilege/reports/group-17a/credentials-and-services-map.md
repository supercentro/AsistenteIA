# Credentials, identities and services: dependency map and safe order (group 17A)

Names only: this document contains no value and the procedures below never print one. Everything here was rehearsed on the replica of `run_17a_replica.sh`; nothing was applied to the development stack.

## 1. Identities

| Identity (PostgreSQL role) | Who uses it | Where its credential lives today | Where it will live after 17B | Created / changed by |
|---|---|---|---|---|
| `asistente` (administrator, superuser, owner of everything) | the `db` container (initial password only), **today also the API and the worker** (TD-040), the host-side tests (`TEST_ADMIN_DATABASE_URL`) | `backend/.env.db` (`POSTGRES_PASSWORD`), `DATABASE_URL` of `backend/.env` and `backend/.env.worker` | `backend/.env.db`, `ADMIN_DATABASE_URL` of `backend/.env.roles` (read only by the `bootstrap` one-shot and the rollback), `backend/.env.test` for the host tests; **no longer** in `.env` and `.env.worker` | exists; its password is rotated in step 17B.6 |
| `asistente_migrator` (owner of the tables, runs Alembic, no login to the data from the services) | the `migrate` one-shot, `db-verify`, the rollback commands | does not exist | `MIGRATION_DATABASE_URL` of `backend/.env.migrate` | `db-bootstrap` (role) and `db-adopt` (ownership) |
| `asistente_app` | the API process (`backend` service) | does not exist | `DATABASE_URL` of `backend/.env` | `db-bootstrap` (role and password), `prepare_env_files.py` (file) |
| `asistente_worker` | the ingestion worker (`worker` service) | does not exist | `DATABASE_URL` of `backend/.env.worker` | same |
| `asistente_cli` | `create-teacher` and `seed` (profile `cli`, on demand) | does not exist | `CLI_DATABASE_URL` of `backend/.env.cli` | same |

Other secrets: `JWT_SECRET` (API file only, unchanged), the role passwords (four new random values, generated by `prepare_env_files.py` and stored only in `.env.roles` and in the URL of each service file). Nothing else changes.

## 2. Which service reads which file

| Service (compose) | File | Variables (names) | After 17B |
|---|---|---|---|
| `db` | `.env.db` | `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | unchanged, except the password after the rotation |
| `bootstrap` (one-shot) | `.env.roles` | `ADMIN_DATABASE_URL`, `DB_*_PASSWORD` | new file |
| `migrate` (one-shot) | `.env.migrate` | `MIGRATION_DATABASE_URL` | new file |
| `cli` (profile `cli`) | `.env.cli` | `CLI_DATABASE_URL` | new file |
| `backend` | `.env` | `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGINS`, ... | `DATABASE_URL` user and password only |
| `worker` | `.env.worker` | `DATABASE_URL`, ingestion settings | `DATABASE_URL` user and password only |
| host tests | `.env.test` | `TEST_DATABASE_URL`, `TEST_ADMIN_DATABASE_URL` | unchanged (rotated administrator password if it appears there) |

Compose runs `bootstrap` and `migrate` on **every** `up` (the services `backend` and `worker` depend on them): both are idempotent, but the very first `bootstrap` exits **1** (it reports the ownership drift of the old tables), which would stop `migrate`, `backend` and `worker` from starting. That is why 17B runs the first bootstrap by hand and recreates the two services with `--no-deps`.

## 3. Safe order (17B), with what each step needs

1. Preflight and backup (needs only the administrator, read only).
2. **Stop `backend` and `worker`.** (They hold sessions as the administrator; the adoption refuses while any session holds the database. The new code also refuses to start as a superuser.)
3. `prepare_env_files.py` creates `.env.roles`, `.env.migrate`, `.env.cli` and rewrites the two `DATABASE_URL` values, after copying the three old files to `*.pre-17b`. It reads `.env.db` for the administrator and writes four new random passwords. It prints names only.
4. `bootstrap` (first run, exit 1 expected) creates the roles with the passwords of `.env.roles`.
5. `db-adopt` (dry run, then `--apply`) makes the migrator the owner.
6. `migrate` (Alembic 0006 and the grants), then `db-verify`.
7. Recreate `backend` and `worker` with `--no-deps` (they now read the restricted URLs); check `current_user` per session.
8. Functional validation, then cleanup of the synthetic rows.
9. **Only after the acceptance period:** rotate the administrator password (section 4), then destroy the `*.pre-17b` copies.

Why this order: the roles must exist before the services receive their URLs; the services must be down during the adoption; the administrator password is rotated last so that the rollback files (`*.pre-17b`) stay usable until the owner accepts, and it is rotated **after** the services stopped using it, so no service has to be restarted for the rotation.

## 4. Rotation of the administrator password (TD-038 and the incident of 2026-11-13)

**Superseded in its commands by `../group-17b/rotation/README-17b6.md`** (tested tools: nothing is edited by hand, the password never travels in an argument). The text below stays as the rationale and the original rehearsal.

Rehearsed on the replica (the services kept running; the whole step took about 8 s including the recreation of the database container; the API reconnected by itself).

1. Generate the new value outside the repository (password manager) into a file only your user can read, `<NEWFILE>` (letters, digits, `-` and `_` only, so that it needs no quoting). Never on a command line.
2. Change the role through a `psql` session fed from standard input (this is the form rehearsed; the value is read by the shell builtin `printf`, never an argument of an external command):
   ```bash
   export MSYS_NO_PATHCONV=1
   printf "ALTER ROLE asistente PASSWORD '%s';\n" "$(cat <NEWFILE>)" | docker exec -i asistenteia-db-1 sh -c 'psql -U "$POSTGRES_USER" -d postgres -v ON_ERROR_STOP=1 -q -f -'
   ```
3. Replace the value in `.env.db`, `.env.roles` and `.env.test` (after `--strip-legacy` the `TEST_DATABASE_URL` of the host tests lives there; before it, it lived in `.env`, which the final preflight found: the real `.env` carried `POSTGRES_*` and `TEST_DATABASE_URL`). After 17B `.env` and `.env.worker` no longer contain the administrator password, which `prepare_env_files.py --strip-legacy` guarantees by refusing to continue otherwise.
4. Recreate only the database container so that its environment follows the file: `docker compose up -d --no-deps --force-recreate db` (a container keeps the environment it was created with, lesson L29). The data volume is untouched.
5. Check: the old password is refused over TCP, the new one accepted, `bootstrap` again exits 0, the API answers.

   **If the rotation stops half way** (the order above makes step 2 the point of no return): (a) the `ALTER ROLE` failed: nothing changed, the files still hold the old password, leave them and retry; (b) the `ALTER ROLE` succeeded but a file still has the old value: the new value is in the password manager, so write it into the file(s) by hand with an editor and recreate `db` (step 4); the services keep their open connections and fail on the next reconnect with an authentication error in their log (the API reconnects on a pooled connection failure only after the files are right); (c) never run the rollback of the files (`--rollback`) in this state: it copies the administrator password from `.env.db`, which must already hold the NEW value.
6. Destroy `.env.pre-17b`, `.env.worker.pre-17b` and `.env.db.pre-17b` (they hold the exposed value). Do not rewrite or delete the subagent transcript of the incident without the owner's decision (it is an audit record); after the rotation the value in it is harmless.
7. Record the date in `docs/technical-debt.md` (TD-038) and close the incident.

If the rotation is done **before** the rollback is needed, `prepare_env_files.py --rollback` rebuilds the old `.env` and `.env.worker` with the administrator password of the **current** `.env.db`, so a rollback never reintroduces the exposed value (rehearsed).

## 5. What the owner must provide or decide before 17B

- The authorisation of task 3.3b (the creation of `.env.roles`, `.env.migrate`, `.env.cli` and the edit of the two `DATABASE_URL` lines in the real files) as part of the 17B authorisation.
- A password manager entry for the new administrator password (step 4 of section 4) and a window in which a short restart of `db` is acceptable.
- Whether `backend/.env.test` holds `TEST_ADMIN_DATABASE_URL` for the administrator (then it must follow the rotation).
