## What the workflow does

Triggers: `push` (any branch) and `pull_request`. Permissions: `contents: read`. Three independent jobs on `ubuntu-latest`:

| Job | Limit | What it runs |
|---|---|---|
| `backend` | 30 min | `uv sync --frozen`, ruff check, ruff format check, mypy strict, unit tests, ordinary integration tests (`-m "not role_bound and not realmodel"`) on one `pgvector/pgvector:0.8.7-pg15` service, non-blocking `pip-audit` |
| `privileges` | 40 min | two exclusive service clusters (`pgvector/pgvector:0.8.7-pg15`), then `prerequisites`, `clusters`, `flow` (bootstrap, migrations to 0006 with grants, `db-verify`, `alembic check`, second idempotent pass), `drift-selfcheck`, `privilege-unit`, `role-suites`, `roles-mode`, `summary` (`if: always()`) |
| `frontend` | 30 min | npm ci, lint, format, typecheck, `check:api-types`, Vitest with coverage, build, Playwright (mocked) |

## Dependencies that must hold

- The repository on GitHub exists and Actions are enabled (`origin` is `https://github.com/supercentro/AsistenteIA.git`; whether Actions are enabled and which minutes are available is an owner fact that this plan could not check without a remote call).
- The runner can pull `pgvector/pgvector:0.8.7-pg15`, `astral-sh/setup-uv@v5` (uv 0.12.9), `actions/checkout@v4`, `actions/setup-node@v4`. Most of these are already used by `main`'s workflow, which is green.
- No secret is needed: the JWT secret and every password are generated by the job and masked before they reach the environment.
- The fork rule: a pull request from a fork would run with a read-only token and no secrets; there is no `pull_request_target` trigger.

## Procedure (for the owner to authorise; commands for the day, not executed)

1. Check that the working tree is clean and that the last local gates are green (`openspec validate --all --strict`, ruff, mypy, the unit and integration commands of `docs/development_guide.md`).
2. **Push the branch only** (this triggers the `push` workflow, without a pull request and without the duplicate `pull_request` run): `git push -u origin feature/database-least-privilege`.
3. Watch the run: `gh run list --branch feature/database-least-privilege`, then `gh run watch <id>` or the Actions page. Collect the logs of the `privileges` job (`gh run view <id> --log`) into the change's reports.
4. Do **not** open the pull request, apply branch protection or merge until the acceptance criteria below are met.

## Risks (TD-045) and what to do when it fails

| Risk | What it would look like | Action |
|---|---|---|
| Service cluster not ready when the first step connects (`pg_isready` uses the socket; nothing retries the first connection) | `prerequisites` or `clusters` fail at once | re-run the job once; if it repeats, add a retry loop in `step_clusters` with a test first |
| Wall-clock tests on the shared runner (heartbeat, lease fencing, upload concurrency, per-role connection limits) | a single failing test with a timing assertion | reproduce locally with `run_gate_local.sh` under CPU limits; fix the test with TDD; never raise a floor or skip the test to get a green |
| Different Python or uv resolution | import or lock errors | `uv sync --frozen` fails on a lock drift: fix the lock locally |
| `MIN_*` floors tight (484 against 480) | a legitimate removal of a few tests fails the gate | change the script floors in a reviewed commit, not by environment override |
| Windows versus Linux paths in scripts | a script fails on the runner only | reproduce in the Linux runner of `run_linux_tests.sh` |
| The superuser refusal (15.2) in child-process tests | a real-server test fails with "refusing to start" | the test must pass `superuser_exception()`; fix the test |

On any failure: do not merge, keep the failing log in `reports/`, reproduce locally, fix with a failing test first, push again (each push is a new run). A run that is red for an infrastructure reason (runner or registry outage) is re-run once and recorded as such; a second red is treated as a defect.
