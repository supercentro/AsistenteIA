# `.env.test` and the administrator credential: decision record (TD-038, read from the code; no value was read or printed)

## Facts (names and code only)

- `backend/.env.test.example` declares exactly two variables, both host-only (no container receives the file): `TEST_DATABASE_URL` (database `asistenteia_test`, today as the cluster administrator `asistente`) and `TEST_ADMIN_DATABASE_URL` (maintenance database `postgres`, same server, administrator). After `--strip-legacy` the real file will hold the former `TEST_DATABASE_URL` of `backend/.env`, i.e. the administrator password.
- Who reads them: `tests/db_support.py` (`require_test_database_url`, `require_test_admin_database_url`), `tests/integration/conftest.py`, `tests/db_admin_support.py`, `tests/least_privilege.py`. Guards: the test database name must end in `_test`, must differ from `DATABASE_URL`, and the admin URL must name the same server.
- What the tests do with them, and why a plain role is not enough:
  - `drop_everything()` runs `DROP SCHEMA public CASCADE`, `CREATE SCHEMA public` and `DROP EXTENSION IF EXISTS vector CASCADE`; migration `0001` and the bootstrap run `CREATE EXTENSION IF NOT EXISTS vector`. The `vector` extension of the pinned image (`pgvector 0.8.7`) is **not marked `trusted`** (its control file has no `trusted = true`), so only a superuser can create it.
  - The role-bound suites `CREATE`/`DROP DATABASE ... WITH (FORCE)`, create and drop roles with the reserved test prefix, and some tests run `ALTER ROLE ... SUPERUSER BYPASSRLS CREATEROLE` to prove that `db-verify` detects it; granting `SUPERUSER` needs a superuser.

## Decision

1. **Both test URLs genuinely need a superuser of the test cluster.** A segregated role with minimum privileges (owner of `asistenteia_test` only, or `CREATEROLE`/`CREATEDB` without `SUPERUSER`) cannot run these suites. It would also buy no isolation while the test cluster is the development cluster (a superuser is a superuser).
2. **What segregation is possible and worth doing**: give the tests their **own throw-away PostgreSQL cluster** (own container or `run_gate_local.sh`-style cluster, own port, own volume, own superuser and its own password), and point `.env.test` at it. Then `.env.test` never holds the development administrator password, a leaked test credential cannot touch the development database, and `.env.test` is out of the rotation of TD-038. The code already supports it (the URLs are only host and database names; the guard compares them with `DATABASE_URL`). It needs a small, separate change (an optional Compose service in a profile, or a documented command) and the owner's approval; it is **not** part of 17B.2.
3. **Until then** (and this is what the rotation must assume): after `--strip-legacy` `.env.test` holds the development administrator credential, because the host tests run against `127.0.0.1:5442`. Its scope is limited to the owner's workstation (host-only file, git-ignored, owner-only descriptor `Modify` since S21), and it **is rotated with the other two files** by `rotate_admin_password.py` (it updates every URL variable whose user is the administrator and leaves URLs of other users untouched).
4. If the owner prefers not to keep an administrator credential for the tests on the development cluster at all, the tests simply stay unrun on this machine until decision 2 is implemented; nothing else depends on `.env.test` (the API, the worker, the CLI, the migrator and CI never read it).
