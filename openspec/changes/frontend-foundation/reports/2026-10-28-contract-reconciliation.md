# Contract Reconciliation - frontend-foundation

Method: `docs/api-spec.yml` compared with the OpenAPI document generated by the backend (`create_app(...).openapi()`, script kept in the session scratchpad, run against the unreachable test database URL because the schema does not need a connection) and, later, with the observed responses of the running stack (`step-11` report).

| Schema | `api-spec.yml` before | Backend OpenAPI (`required`) | Action |
|---|---|---|---|
| `User` / `UserResponse` | no `required` | `id`, `name`, `email`, `role`, `consent_version`, `consent_accepted_at` | Declared all six `required` (the two consent fields stay nullable). Evidence: backend schema and every observed response |
| `Subject` / `SubjectResponse` | `required: [id, teacher_id, created_at]` + `SubjectCreate` (`description` optional) | `id`, `name`, `description`, `teacher_id`, `created_at` | Added `description` to `Subject.required` (nullable). `name` is already required through `SubjectCreate` |
| `TokenResponse` | `required: [access_token, token_type, expires_in]` | `access_token`, `expires_in` (`token_type` has a default and is always serialised) | Unchanged; the frontend reads `access_token` and `expires_in` only |
| `RegisterRequest` | `name`, `email`, `password` required | same | Unchanged |
| login request | inline, `email`, `password` required | `LoginRequest` same | Unchanged |
| `Error` | `code`, `message` required, `details` nullable | `ErrorResponse` same | Unchanged |

Other schemas (`Document`, `Conversation`, `Message`, `Source`) have no `required` list either, but they belong to later changes and are not used here; they are left as they are and noted for changes 5 to 10.

No incompatibility that would require changing the approved contract or the backend behaviour was found. The two corrections only add `required` to fields the backend always returns.
