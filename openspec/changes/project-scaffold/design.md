# Design

## Context

Greenfield repository: documentation only, `main` clean, no `backend/` or `frontend/`. The stack and layering are fixed by `docs/backend-standards.md`, `docs/frontend-standards.md` and `docs/development_guide.md`; this design only records the choices those documents leave open for the scaffold. Motivation and scope: see `proposal.md`; behaviour: see `specs/`.

Local toolchain observed: Docker 29, uv 0.12, Node 24, npm 11, Python 3.13 (the project pins 3.12, which `uv` provisions). Already decided by the user: synchronous SQLAlchemy, JWT in memory on the frontend, fake LLM/embedding providers for automated tests.

## Goals / Non-Goals

**Goals:**
- A skeleton where every later change adds files to an existing, tested structure instead of creating infrastructure.
- Every MUST gate of `docs/base-standards.md` §9 that can apply to a scaffold (typing, lint, migrations on clean DB, `docker compose up`, lock files, no secrets) passes from day one.
- Keep the change small: no business tables, no auth, no ML dependencies.

**Non-Goals:**
- Auth, users, subjects, documents, chat, consent, GDPR deletion, seed/CLI, deployment, committed end-to-end flow (later changes 2–13).
- Production-hardening of images beyond a non-root user and pinned bases.

## Decisions

**D1. Sync SQLAlchemy 2.x with `psycopg` 3 (`postgresql+psycopg://`).** Matches the approved sync decision and the `DATABASE_URL` in the development guide. Sync routes run in FastAPI's threadpool; CPU-bound embedding work later also stays off the event loop. Alternative: async + asyncpg (rejected by the user).

**D2. Backend layout exactly as `backend-standards.md` §2.** Packages `api/v1/endpoints`, `api/deps.py`, `services`, `repositories`, `models`, `schemas`, `core`, `rag`, `main.py`; tests in `tests/unit` and `tests/integration`. Empty layers contain only `__init__.py` (no speculative classes). Router assembly under `/api/v1`.

**D3. Settings via `pydantic-settings` in `core/config.py`.** Only variables consumed by code in this change are declared and documented: `DATABASE_URL` (required, no default so no credentials live in code), `APP_ENV` (`development` | `test` | `production`, default `development`), `CORS_ORIGINS` (default `http://localhost:5173` only when `APP_ENV=development`; explicit and mandatory in `production`; `*` rejected in every environment) `LOG_LEVEL` (default `INFO`) and `DB_CONNECT_TIMEOUT_SECONDS` (default 5, range 1-60, see D12). `TEST_DATABASE_URL` is **not** part of `Settings`: it is read only by the integration-test fixtures, so a normal startup never needs or validates it. Each later change adds its own variables (JWT, Gemini, embeddings, upload limits) to both the settings class and `.env.example`. Missing required variables fail at import/startup. Alternative: declare everything in the development guide up front (rejected: unused config invites drift and unverified placeholders).

**D4. Transaction per request in a dependency (`get_db`).** Yields a session, commits after successful handling, rolls back on exception; services never commit (`backend-standards` §3). Models share a `DeclarativeBase` with an explicit constraint naming convention so autogenerated Alembic migrations are deterministic.

**D5. Errors.** `core/errors.py` defines `AppError` plus `NotFoundError`, `ForbiddenError`, `ConflictError`, `UnauthorizedError`; LLM/search errors are added by the chat change. Handlers return the `Error` schema: codes `NOT_FOUND`, `FORBIDDEN`, `CONFLICT`, `UNAUTHORIZED`, `VALIDATION_ERROR`, `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE`. The 422 handler builds `details` from field locations/messages only, never from submitted input. The generic handler logs the exception type and a request id, never bodies.

**D6. CORS and secure headers.** Starlette `CORSMiddleware` with `allow_origins=CORS_ORIGINS` (explicit list; no `*`) and a small middleware adding `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`. HTTPS enforcement stays with the hosting platform (`backend-standards` §8).

**D7. Alembic with a single initial revision `CREATE EXTENSION IF NOT EXISTS vector`; downgrade `DROP EXTENSION IF EXISTS vector`.** Python `pgvector` package is not added yet (first needed by the schema change). Migration test connects to a real PostgreSQL 15 + pgvector database (`TEST_DATABASE_URL`, separate `asistenteia_test` database in the compose `db` service and a service container in CI) and runs upgrade → downgrade → upgrade.

**D12. Connection timeout.** The engine passes libpq `connect_timeout` (`DB_CONNECT_TIMEOUT_SECONDS`, default 5, validated 1-60) so an unreachable or silent database fails fast and `/health` answers 503 instead of hanging (observed with an IPv6/IPv4 mismatch during development). It bounds connection establishment only, not query duration (statement timeouts are a later concern). Covered by unit tests (default, override, range, driver argument) and an integration test against a TCP server that accepts but never answers.

**D11. Test database isolation guard (behaviour as implemented).** `app/core/db_safety.py` exposes `assert_safe_test_database(test_url, app_url, app_env)`. Checks, in order: (1) `APP_ENV` is not `production`; (2) `test_url` parses; (3) its database name ends in `_test`; (4) if `DATABASE_URL` is available, its database name differs from the application database name **regardless of host or port** (stricter than "same server and name": `db` and `127.0.0.1` can be one server). If `DATABASE_URL` is absent only checks 1–3 apply. Error messages never contain the password or the full URL. `APP_ENV`/`DATABASE_URL` are read from the process environment; the integration `conftest` first loads `backend/.env` without overriding real variables.

Enforcement points, all in `tests/`: `require_test_database_url()` (session fixture; a missing variable or a rejection calls `pytest.exit` with code 2, before any connection and before any test runs) and `guarded_engine()` (re-runs the guard before every connection used by destructive helpers such as `drop_everything`). The Alembic config used by tests receives its URL only from the guarded fixture; `alembic/env.py` keeps using `DATABASE_URL` for normal manual runs.

Limits (accepted): the guard is a naming and environment convention, not a privilege boundary, and it does not intercept a developer running `alembic downgrade` manually against `DATABASE_URL`; both databases live in the same PostgreSQL server with the same role. The compose `db` service creates `asistenteia_test` through an init script (`docker-entrypoint-initdb.d`); CI creates it with a setup step. A missing `TEST_DATABASE_URL` makes integration tests fail fast with a clear message before any connection. Alternative: a separate PostgreSQL container for tests (stronger isolation, heavier; rejected for the MVP, a distinct guarded database is enough).

**D8. `/health` behaviour (contract extension — needs approval).** `docs/api-spec.yml` documents only the 200. The endpoint is described as a "database connectivity check", so a failure must be observable: respond 503 with the `Error` schema (`SERVICE_UNAVAILABLE`), no details. The same change documents the generic error codes in `docs/api-spec.yml`. Alternative: always 200 (pure liveness) — rejected because it hides a down database from compose/CI/platform checks.

**D9. Frontend scaffold.** Vite + React 18 + TS strict + Tailwind; React Router and TanStack Query providers wired around a single placeholder home page; Axios instance in `lib/` reading `VITE_API_URL` (no auth interceptor yet; token-in-memory handling belongs to the auth/frontend changes); `lib/strings.es.ts` as the single Spanish-copy module; empty `components/hooks/services/types/tests` folders. Tooling: ESLint (typescript-eslint, react-hooks, jsx-a11y), Prettier, Vitest + React Testing Library + MSW, Playwright Test with one smoke spec (`npm run test:e2e` loads the page). Headless UI, React Hook Form and Zod are added by the first change that uses them. Alternative: install the whole stack now (rejected: unused dependencies, no way to verify them).

**D10. Docker and CI.**
- `docker-compose.yml`: `db` (`pgvector/pgvector:pg15`, healthcheck, named volume), `backend` (waits for healthy db; migrations stay a manual `alembic upgrade head` as in the development guide), `frontend` (Vite dev server on 0.0.0.0, source bind-mounted, `node_modules` in an anonymous volume).
- Backend image: pinned `python:3.12-slim`, dependencies via `uv sync --frozen`, non-root user. The embedding model is **not** downloaded here; the development guide's remark about the model download and cache volume moves to the ingestion change.
- CI (`.github/workflows/ci.yml`): backend job with a `pgvector/pgvector:pg15` service, frontend job, `pip-audit` and `npm audit` as non-blocking steps (SHOULD). Playwright Test is not run in CI yet (the committed flow arrives in change 12); no provider secrets are referenced.
- Backend tooling pinned in `pyproject.toml`/`uv.lock`: fastapi, uvicorn, pydantic-settings, sqlalchemy, alembic, psycopg[binary]; dev: pytest, pytest-cov, httpx, ruff, mypy, pip-audit.

## Risks / Trade-offs

- [Local Python is 3.13, project is 3.12] → `uv` pins `requires-python`/`.python-version` to 3.12 and provisions it; verified in task 1.
- [Bind-mounted frontend on Windows is slow / file-watching flaky] → enable polling in the Vite dev server config only inside compose; documented in the guide.
- [Integration tests need a running PostgreSQL] → `docker compose up db` documented as the prerequisite; CI uses a service container.
- [The init script runs only on first volume creation] → the development guide documents `docker compose down -v` or `createdb` as fallback; fixtures fail with a clear message if the test database does not exist.
- [Extension creation requires privileges] → compose database user is the owner of the dev/test databases; documented for Supabase later (`pgvector` is enabled by default there).
- [`/health` 503 extends the contract] → flagged D8; documented in `docs/api-spec.yml` in the same change.
- [Deferring Playwright in CI and ML dependencies] → intentional; the verification step of change 12 and the ingestion change cover them.

## Migration Plan

New directories only; nothing to migrate. Rollback = revert the branch. First database state is created by `alembic upgrade head`.
