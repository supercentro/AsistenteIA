# Technical Debt Register

Central register of residual risks and known limitations accepted when a change was merged. Each item names the change expected to resolve it. This document only **records**; resolving an item happens inside the OpenSpec change listed under "Owner", with the user's approval of scope.

Change numbers refer to the approved 13-change plan (`3` subjects-and-enrollments, `4` frontend-foundation, `5` documents-schema-pgvector, `6` document-ingestion, `7` teacher-material-ui, `8` conversation-persistence, `9` rag-chat, `10` student-chat-ui, `11` personal-data-erasure, `12` e2e-and-quality-closure, `13` deployment-and-delivery-docs). Archived changes are not modified.

## Conventions

- **Priority**: High (blocks a safe release or a mandatory feature), Medium (should be handled before delivery), Low (accept or revisit on evidence).
- **Status**: `open` (not started), `planned` (assigned to an upcoming change's tasks), `accepted` (deliberate trade-off, revisit only on evidence), `resolved` (fixed; keep the row and link the change).
- **Owner**: the change that should resolve it, or `Future feature` when it is outside the approved MVP and needs user approval before being planned (see `docs/base-standards.md` section 8).
- Add a new row (next free ID) whenever a change is merged with a known residual risk; update the status instead of deleting rows.

| TD-022 | The HNSW index `ix_document_chunks_embedding` is not used by the current plan: `find_similar` orders by `embedding <=> :query, id` (the `id` tie-break) and filters by subject first, so the planner reads the subject's chunks through the b-tree indexes and sorts them exactly. The index costs writes at ingestion without any read benefit yet, and the search cost grows with the chunks of one subject. Dropping the `id` tie-break would not make the index useful and would bring back the risk of incomplete filtered results (design D3); no automated guard detects a plan change yet (TD-026) | Low | None for the MVP corpus (recall 1.00 and 0.3 to 2.6 ms measured with up to 30,060 chunks in 600 subjects); a subject with a very large corpus would slow down and the index would be dead weight | Exact filter-first search is the functional reference (design D3); evidence in `openspec/changes/documents-schema-pgvector/reports/2026-11-07-explain-and-recall.md`; no planner or pgvector setting, index or ORDER BY was changed | Change 12 (performance evaluation and indexing strategy; options in the report; any change needs user approval) | open |
| TD-023 | There is no quota on documents per subject or chunks per document or subject, and the database imposes no size cap beyond `size_bytes >= 0` | Low | A teacher (or a bug in ingestion) could store very many chunks; the exact search reads every chunk of one subject, so search time and storage grow with it; no `statement_timeout` or work bound limits an exact sort over a very large subject. Evaluate a `statement_timeout` (and caps on chunks per document or subject) before any bulk load | Upload size limit and file-type validation planned at ingestion (change 6); search cost measured in `reports/2026-11-07-explain-and-recall.md` | Change 6 (limits at upload) and change 12 (evidence with real volumes) | open |
| TD-024 | The embedding dimension is fixed in the schema (`vector(384)`, model `paraphrase-multilingual-MiniLM-L12-v2`) and the accepted norm range `1e-6` to `1e6` was measured on pgvector 0.8.7; the range is applied to the single-precision values the database stores (the helper never accepts what the CHECK rejects since finding F5, so a double norm of exactly `1e-6` is rejected, the smallest accepted norm is the next single-precision value, and a relative margin of `1e-12` around both limits rejects norms the sum order of pgvector could decide differently; acceptance implies the CHECK passes, the reverse is not guaranteed; the margin assumes 384 dimensions and that pgvector accumulates `vector_norm` in double precision as 0.8.7 does, so re-check it when either changes) | Low | A different embedding model or dimension needs a new migration plus re-embedding of every chunk; a pgvector upgrade can change which magnitudes are reliable | The model is fixed for the MVP; the image is pinned to `0.8.7-pg15`; the upgrade procedure (rerun the magnitude experiment, `ALTER EXTENSION vector UPDATE`) is in `docs/development_guide.md` | Future feature (model change); whoever upgrades pgvector | accepted |
| TD-025 | The hnsw parameters are the defaults (`m=16`, `ef_construction=64`, no `ef_search` tuning) and the behaviour of approximate search combined with a subject filter was not evaluated, because the current plan does not use the index (TD-022) | Low | If the strategy later moves to approximate search, a filter applied after the index scan can return fewer rows than `top_k` (design D3) | Exact filter-first search; recall 1.00 measured against an exact ranking up to 30,060 chunks in 600 subjects | Change 12 (with real data; any setting change needs user approval) | open |
| TD-026 | There is no automated guard that fails if the planner starts using the HNSW index or if the `id` tie-break is removed from `find_similar` (the recall test only detects the tie-break by `test_ties_are_broken_by_chunk_id`; no `EXPLAIN` assertion exists). Proposed by the independent review of group 11 and registered here pending the user's decision on the guard test | Low | A later edit of the query could silently switch to approximate filtered search and return fewer than `top_k` rows (design D3) without any test failing | Documented in TD-022 and design D3; the tie-break test kills the removal of `, id` | Change 12 (decide and add the `EXPLAIN` guard together with the indexing strategy) or earlier if the user approves the test | open |
| TD-027 | The non-empty content check `content ~ '\S'` of `document_chunks` accepts content made only of characters that PostgreSQL does not classify as whitespace in the database locale but that look blank, such as U+00A0 (no-break space) or U+0085 (next line). Same family as TD-018 | Low | A chunk with visually empty content could be stored and later retrieved as a source; it carries no secret and cannot cross subjects, but it adds noise to answers and citations | Migration `0004` and the applied constraints are deliberately unchanged (user decision, 2026-11-08); the ingestion of change 6 should normalise or reject such content before it reaches the database | Change 6 (`document-ingestion`: normalise content, then reconsider a stricter CHECK in a new migration) | accepted |
